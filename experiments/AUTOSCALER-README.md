# Эксперимент 2: динамическое горизонтальное масштабирование (автоскейлер)

## Цель

Продемонстрировать работу системы автоматического масштабирования
post-service в зависимости от текущей нагрузки. Проверить, что
автоскейлер корректно реагирует на изменения метрик и защищён от
характерных проблем — флаппинга и реакции на кратковременные всплески.

## Связь с Экспериментом 1

В Эксперименте 1 (статическое масштабирование) была определена
**зависимость RPS от числа реплик** и точка насыщения. Эксперимент 2
**использует эти знания**: верхняя граница автоскейлера (`MAX_REPLICAS`)
выставлена по найденной точке насыщения — масштабироваться дальше
бессмысленно, узким местом становится БД.

## Архитектура

```
k6 -> gateway -> nginx -> [post-service × N] -> postgres + redis
                              ↑
                       autoscaler ←—— Prometheus
                              ↓
                       Docker API
```

**Autoscaler** — собственная реализация, прототип Kubernetes HPA:
- Раз в 10 секунд опрашивает Prometheus
- Получает p95 latency шлюза за последние 30 секунд
- Сравнивает с порогами и принимает решение

## Политика масштабирования

| Условие | Действие |
|---|---|
| p95 > 500 мс **2 цикла подряд** (≈10 сек) | +1 реплика |
| p95 < 100 мс **6 циклов подряд** (≈30 сек) | -1 реплика |
| Прошло меньше 15 секунд после действия | пропуск (cooldown) |
| Реплик меньше `MIN_REPLICAS` | scale up даже без метрик |
| Реплик больше `MAX_REPLICAS` | scale up запрещён |

> **Примечание.** Параметры подобраны под короткий профиль нагрузки (3.5 мин).
> Для длительных production-сценариев их следует увеличить:
> `SCALE_UP_AFTER_N=3` (30 сек), `SCALE_DOWN_AFTER_N=12` (2 минуты),
> `COOLDOWN_AFTER_SCALE_MS=30000` (30 сек). В коротком эксперименте такие
> значения не дают автоскейлеру успеть отработать.

### Защита от типичных проблем

**Флаппинг (быстрые колебания).** Если просто "если latency > X, скейлим",
система начнёт дёргаться: подняли реплику → latency упал → опустили реплику →
latency вырос → подняли... Решено двумя механизмами:
1. **Cooldown** — после каждого действия 30 секунд автоскейлер не реагирует.
2. **N циклов подряд** — порог должен держаться несколько измерений,
   а не сработать на один всплеск.

**Асимметричные пороги.** Поднимать вверх быстро (через 30 сек),
опускать вниз медленно (через 2 минуты). Объяснение: ошибка
"оставили лишнюю реплику на минуту" дешевле, чем "не успели поднять
реплику, пользователи получили таймауты".

**Cold start.** Новая реплика стартует не мгновенно. Cooldown 30 сек
покрывает время её прогрева — до этого автоскейлер не примет следующее
решение, иначе мог бы поднять "лестницу" реплик зря.

## Профиль нагрузки

Пилообразный, специально подобран, чтобы пройти все режимы автоскейлера
за короткое время:

```
VU
200 │       _________          ___________
150 │      ╱         ╲        ╱           ╲
100 │     ╱           ╲      ╱             ╲
 20 │    ╱             ╲____╱               ╲
 10 │___╱                                    ╲___
    └─────────────────────────────────────────→ time
    0:00  0:30  1:00  1:30  2:00  2:30  3:00  3:30

    фаза 1 (0:00-0:30): разогрев на 10 VU
    фаза 2 (0:30-1:30): рост до 200 VU         ← должен сработать scale up
    фаза 3 (1:30-2:00): плато на 200 VU        ← закрепление реплик
    фаза 4 (2:00-2:30): спад до 20 VU          ← должен сработать scale down
    фаза 5 (2:30-3:00): второй пик до 200 VU   ← повторный scale up
    фаза 6 (3:00-3:30): финальный спад
```

Общая длительность: **~3.5 минуты**.

## Запуск

```bash
chmod +x experiments/autoscaler-experiment.sh
./experiments/autoscaler-experiment.sh
```

Скрипт:
1. Поднимает стенд с 1 репликой post-service
2. Запускает в фоне сбор временных рядов (число реплик, p95, состояние счётчиков) каждые 5 сек
3. Запускает k6 с пилообразной нагрузкой на 12 минут
4. Собирает логи автоскейлера
5. Выводит сводку решений

## Артефакты

## Ожидаемые результаты

### Главный график (для защиты)

По оси X — время, две оси Y:
- **Левая ось:** число реплик (синяя ступенчатая линия)
- **Правая ось:** p95 latency (оранжевая линия)

Должно быть видно:
1. При росте нагрузки сначала растёт latency
2. Через ~30 сек автоскейлер добавляет реплику → latency падает
3. При спаде нагрузки latency держится низко 2 минуты
4. Автоскейлер уменьшает число реплик

## Что показывает эксперимент

1. **Принцип элазстичности** — система автоматически адаптируется к нагрузке
2. **Реактивность** — задержка реакции (30-60 сек) и её причины (cooldown, N циклов)
3. **Защита от флаппинга** — стабильность поведения
4. **Ограничения сверху** — точка, где увеличение реплик не помогает (БД)

## Сравнение с production-решениями (для теоретической главы)

| Аспект | Наш автоскейлер | Kubernetes HPA |
|---|---|---|
| Источник метрик | Prometheus (custom-query) | Metrics Server / Prometheus Adapter |
| Управление | Docker API | Kubernetes API |
| Cooldown | Глобальный, 30с | stabilizationWindowSeconds (раздельно для up/down) |
| Алгоритм | "N циклов подряд" | Скользящее окно + усреднение |
| Min/max | env-переменные | `minReplicas` / `maxReplicas` в манифесте |
| Multi-metric | p95 latency | CPU + Memory + Custom (любая комбинация) |

В рамках дипломной работы реализован упрощённый аналог HPA,
**достаточный для демонстрации принципа** и проведения исследования.
В production-средах применяется Kubernetes HPA или аналоги
(KEDA, Google Cloud Autoscaler, AWS Auto Scaling).
